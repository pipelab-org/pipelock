# `pipelock check`

Validate a config file with `pipelock check --config pipelock.yaml`. Add `--url` to test a URL against that config's scanner. Add `--require-build-compatibility` to reject configuration that the selected binary can't enforce.

## Validate for the local service

On Linux with systemd, validate a candidate using the configuration environment of the local system `pipelock.service`:

```bash
sudo pipelock check --config /etc/pipelock/pipelock.yaml --service pipelock
```

This mode reads the manager's environment and the loaded unit's effective `Environment`, ordered `EnvironmentFiles`, and `UnsetEnvironment` properties. Systemd resolves drop-in ordering, resets, and unit specifiers. Environment-file values stay literal; the checker doesn't expand shell expressions. Later files override earlier assignments, and unsets apply last. An optional file that is missing or cannot be opened or read contributes no assignments, matching systemd. A readable file with unsupported syntax still causes refusal. Comment continuations, quoting, and escapes follow systemd's environment-file grammar. In unquoted values, whitespace immediately before a backslash-newline is preserved; trailing whitespace added after the continuation is trimmed. The running manager's version selects comment-escape behavior: before systemd 254, an escaped newline keeps the following line inside the comment; from 254 onward, the newline ends the comment and the following line is parsed normally, as recorded in [systemd's v254 NEWS](https://github.com/systemd/systemd/blob/v254/NEWS). This differs from the unit-file continuation rules in [systemd.syntax(7)](https://github.com/systemd/systemd/blob/v254/man/systemd.syntax.xml). An unresolved manager version causes refusal. Invalid variable names, unterminated quotes or escapes, and prohibited Unicode are refused rather than accepted or ignored as some systemd versions do.

The validator receives only environment variables consumed by config, license, and signing-path readers, including `HOME` and `PIPELOCK_HOME`. It doesn't inherit the invoking shell's environment or pass loader variables to the selected binary. It runs as the static service user with its primary and supplementary groups. Identity resolution uses the binary's `os/user` implementation; builds without cgo require local account and group records and cannot resolve an identity supplied only by NSS. Root can switch to that identity; an unprivileged caller must already have that identity and those groups. Candidate bytes arrive over stdin, and relative companion files resolve from the candidate's directory. The selected executable must be a regular file rather than a symlink.

Success prints `Config validation: OK (valid for pipelock.service configuration environment)`. This checks configuration inputs on the host. It doesn't recreate the service's mount namespace or certify file accessibility inside its sandbox. The service must still start successfully. The unit properties, environment files, identity, and candidate config are observed again after validation; changes cause refusal and require a retry.

Only `pipelock` and `pipelock.service` are supported. This mode requires a config file path and can't be combined with `--url`. It refuses stale or transient units, nonempty `PassEnvironment`, PAM, dynamic users, credential directives, pre-start or condition commands, root images/directories, custom working directories, primary-group overrides that differ from the account's primary group, and environment-file globs. Each environment file must be a regular file, not a symlink, and no larger than 64 KiB. The candidate config is read the way `pipelock check --config` reads it: a symlinked path is followed and there is no size limit. Successful introspection and the running manager's version determine which newer directives an older manager supports. Present properties require successful typed reads; missing baseline properties cause refusal. Systemd 255 without an explicit `User=` also causes refusal when its login-environment property is ambiguous. Run `systemctl daemon-reload` after editing unit definitions before checking again.

Typed property observations and environment files have a local 64 KiB resource limit. Property discovery uses metadata-only introspection XML, bounded by the D-Bus specification's 128 MiB maximum message size; it does not fetch every property value. Candidate configurations have no size cap. Child output is withheld because config errors can quote secrets. To inspect ordinary config diagnostics separately, use `pipelock check --config /etc/pipelock/pipelock.yaml` in an environment you control; its output can contain configuration values.

`contain install` uses the same validator for its early config preflight. On a first install with no loaded unit, that check uses the manager baseline and planned service identity. After writing the prospective unit and reloading systemd, install validates again against that loaded unit before starting or restarting the service. This prospective check also compares the exact executable, arguments, and execution flags with the managed command, so an overriding command is refused. A failed prospective check rolls back the attempted install. The early real-install check runs after the managed service identity is created, before config promotion. With `--dry-run`, unavailable manager access, identity records, or identity-switch privileges defer service validation and print an explicit `configuration not validated` limitation; the plan can still be inspected. Invalid configurations and unsupported service definitions still refuse whenever validation can inspect them. Real installs always require successful validation.
